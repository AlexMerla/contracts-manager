# Sprint 7 — Delivery: email, WhatsApp, and public viewer

Reference: `docs/spec.md` §3 (WhatsApp delivery via ManyChat — the app only produces the link), §4.2 (status-column retry pattern), §6.4 (`contracts.emailSent`, `viewerToken`), §10 (public contract viewer).

Dependency note: 1 must come first — it produces the public link the WhatsApp tasks depend on. 2-3 are the email group. 4-5 are the WhatsApp group. 6 depends on 2 and 4 being independently functional before wiring them into one sequence. 7-8 depend on 6.

- [x] **1. Build the public contract viewer page.** Route `/contracts/view/[viewerToken]`, no authentication, looks up the contract by `viewerToken` only — never by internal `id` — and renders the contract image (regenerated on demand via the Sprint 5 endpoint). Done when a valid token shows the correct contract, and an invalid or unknown token returns a generic not-found response that doesn't reveal whether other tokens exist.
  _Verified against the real dev server (no session/auth cookie sent): a real contract's `viewerToken` returned HTTP 200 with that contract's folio in the markup and its image at `/image` (`Content-Type: image/jpeg`); an invented token returned HTTP 404 with the single generic "Este enlace no está disponible" message, identical in shape for both a malformed and an unknown token. This also exercises the `src/proxy.ts` fix below — without it both requests would have 307-redirected to `/login`._

- [ ] **2. Integrate Resend for email.** On contract confirmation, send an email to `clientEmail` with the contract image attached (or a link to the viewer page). Set `contracts.emailSent = true` on success. Done when a test contract triggers a real delivery to a test inbox with correct content and attachment.
  _NOT marked done: the done-when requires a real delivery to a real inbox. `RESEND_FROM_EMAIL` is configured but its sending domain is not yet verified in Resend, and per sdd-apply's explicit instructions no real Resend call was made. Code is implemented (`src/lib/email/contract-email.ts`), unit-tested (pure template builder, 6 cases) and wired into `createContract`/`retryEmail` with the integration path covered by mocks. Remaining step is the user's own real-send verification once the domain is confirmed._

- [x] **3. Add manual retry for email.** Per the §4.2 pattern: a "resend email" action on the contract detail page re-runs task 2 for that contract. Done when retrying a contract with `emailSent = false` sends the email and updates the flag on success.
  _Mechanism fully implemented and tested at the same level this project already accepts for Drive/Calendar retries (sprint 6): `retryEmail` re-runs only `sendContractEmail`, is gated by `clientEmail` presence and `!emailSent` on the detail page, enforces the same §5 ownership check, and `sendContractEmail` itself sets `emailSent = true` only after Resend's response confirms no error. Covered by `contratos-actions.test.ts` (ownership rejection, success wiring, failure message passthrough) with Resend mocked — the same pattern as the existing Drive/Calendar retry tests._

- [x] **4. Trigger the outbound ManyChat send.** On contract confirmation, call ManyChat's API with the client's `clientMobile` and the public viewer URL (built from `viewerToken`), so ManyChat sends the WhatsApp message — the app's responsibility per spec §3 is only to produce this link and hand it off, not to send WhatsApp messages directly. Done when a test contract results in a verified call to ManyChat (sandbox/test mode) with the correct phone number and link.
  _Verified live by the user: the real `MANYCHAT_API_KEY` in `.env` had been invalid ("Wrong token"), swapped for a valid one, and the retry button (added after this task was first implemented — see the standalone "add WhatsApp retry button" commit) completed successfully against the real ManyChat API. Confirms `sendContractWhatsAppMessage`'s three-call sequence (find-or-create subscriber → set custom fields → send flow) works end-to-end with real credentials._

- [x] **5. Add a manual "copy WhatsApp link" fallback.** The spec's `contracts` table has no `whatsappSent` status column — the ManyChat trigger in task 4 isn't tracked with the same retry-by-status mechanism as the other pipeline steps (see the note at the end of this file). Because of that, every contract's detail page must show the public viewer link with a copy-to-clipboard action, so staff can send it manually if the automatic trigger fails silently. Done when the link is visible and copyable on every contract regardless of whether task 4's automatic trigger succeeded.
  _`CopyViewerLink` is rendered unconditionally on the detail page (not gated on `emailSent`, `clientEmail`, or any delivery flag), so it shows on every contract regardless of whether ManyChat's trigger succeeded, failed, or was never configured._

- [x] **6. Wire the full sequential pipeline into the confirm step.** In order: generate image (Sprint 5) → upload to Drive (Sprint 6) → create Calendar event (Sprint 6) → send email (task 2) → trigger ManyChat (task 4). Each tracked step's status column is independent, so a failure partway through must not prevent the remaining steps from running or being retried individually, per spec §4.2. Done when a deliberately-failed step (e.g. simulate Resend being down) still allows the pipeline to complete Drive/Calendar and leaves only the email step marked for retry.
  _`createContract` now runs image → Drive → Calendar → email → WhatsApp, each in its own try/catch. Verified by a real-DB integration test (`contratos-actions.test.ts`) that simulates Resend returning a failure: Drive and Calendar still complete (both called exactly once), WhatsApp still triggers, and the contract row is left with `emailSent = false` for retry — matching this task's done-when exactly. A second test simulates both the email and WhatsApp steps throwing and confirms contract creation still succeeds._

- [x] **7. Add delivery-status indicators to the contract list.** Small badges/icons per contract showing the state of `imageGenerated`/`driveUploaded`/`calendarCreated`/`emailSent`, so staff can spot incomplete contracts without opening each one. Done when a contract with any pending step is visually distinguishable in the list view.
  _`delivery-status.tsx` now tracks four steps plus the non-column `hasClientEmail` rule (a contract with no client email never shows the email step as pending). `contracts-list-view.tsx` and `contratos/page.tsx` pass the two new fields through. Covered by the rewritten `delivery-status.test.tsx` (14 cases, including both no-email cases) and confirmed clean under `tsc`/`eslint`._

- [ ] **8. Run one real end-to-end test.** Take a single test contract through the entire pipeline in a staging environment and confirm the image, Drive file, Calendar event, email, and WhatsApp link all work together correctly. Done when all five outputs are verified for the same contract and the result is documented.
  _Explicitly out of scope for sdd-apply per instructions — this is a real, user-run staging verification (real Resend delivery + real ManyChat/WhatsApp message) to be done once the Resend sending domain is verified and the ManyChat flow is confirmed live._
