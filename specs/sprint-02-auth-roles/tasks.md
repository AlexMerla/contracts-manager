- [x] **5. Build the authorization layer.** A shared helper (e.g. `requireRole(role)` and a `scopeToOwner(query, session)` helper) that enforces the spec §5 matrix at the data-access layer — not only in the UI. For a `normal` session, this helper must add the `createdById = session.user.id` filter to `contracts`/`payments`/`notes` queries automatically rather than relying on each route to remember it. Done when a unit test proves a `normal`-role query cannot return another user's data even if the route forgets to filter explicitly.
  - `src/lib/authorization.ts`: `requireRole(session, role)` is the route-level guard (throws `UnauthorizedError`/`ForbiddenError`). `scopeToOwner(session)` is the data-layer enforcement — for `super` it returns the plain shared `prisma` client unchanged; for `normal` it returns `prisma.$extends(...)` with a `$allOperations` interceptor on `contract`/`payment`/`note` that merges an owner condition into every `where`-bearing operation (`findMany`/`findFirst`/`update`/`delete`/`count`/`aggregate`/etc.) — `contract` gets `createdById = session.user.id` directly, `payment`/`note` get it via the relation (`contract.createdById`), matching spec §5's "only on contracts where createdById = self" wording exactly (those two models don't have their own owner column). `create`/`createMany` are deliberately excluded — there's no existing owner to violate, and the creating route is responsible for setting `createdById` itself.
  - **Real Prisma constraint found while testing, not assumed**: `findUnique`/`findUniqueOrThrow` take a `WhereUniqueInput`, which requires the unique field (`id`/`folio`/`viewerToken`) at the top level of `where` — wrapping it in `AND` (the safe approach used for every other operation) fails Prisma's own validation with a real thrown error, confirmed by actually running the test before assuming the fix worked. Fixed with a flat-merge special case for just those two operations, documented in code with its one known limitation (a caller-supplied nested `contract` filter on a payment/note `findUnique` would be silently replaced, not merged — acceptable since that combination isn't used by any route yet).
  - Installed `vitest` (task 3) + wrote `vitest.config.mts` (`.mts` specifically — Vite's native config loader warned about ESM syntax in a `.ts`-as-CJS file and about `__dirname` in an ESM context; fixed both rather than suppressing the warning) with the `@/*` path alias and `dotenv/config` so `DATABASE_URL` loads the same way it does everywhere else in this project.
  - `src/lib/authorization.test.ts` runs against the **real** Supabase database (no mocks, matching this project's established testing pattern) — creates two throwaway users and two throwaway contracts (one per user) plus a throwaway price list, then proves: (1) a `normal` session's `findUnique` on the other user's contract by raw `id` — no explicit owner filter passed — returns `null`; (2) that same session's `findMany({})` with a totally empty filter returns only its own contract; (3) a `super` session is unscoped and can see both. All cleaned up in `afterAll`. `npm run test` (`vitest run`) passes, 3/3.
