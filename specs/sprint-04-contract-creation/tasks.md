Reference: `docs/spec.md` §5 (permission matrix), §6.4 (`contracts`), §6.5 (`contract_packages`), §6.6/§6.7 (`services`/`package_services`), §6.8 (`contract_service_selections`), §6.9/§6.10 (`price_lists`/`package_prices`), §8 (the six-step flow).

Dependency note: 1-5 build the client-side wizard and roughly follow the step order in §8. 6-7 depend on 1-5 being complete (the confirm endpoint needs a finalized payload shape to accept). 8 depends on 6 (there must be contracts before there's anything to list).

  - `src/app/(app)/contratos/nuevo/steps/step-packages.tsx` — quantity stepper's increment button is `disabled={line.quantity >= pkg.maxQuantity}` (confirmed by reading the file directly), packages with no `maxQuantity` get a simple add/remove toggle instead of a stepper. Running order summary present.

- [x] **4. Step 4 — contract data form.** Client name/contact, event type, date/time, celebrant(s), venue name/address, validated with react-hook-form + zod per the stack in §3. Done when required fields block advancing to step 5 and validation errors are shown inline.

- [x] **5. Step 5 — confirm amounts.** Compute the subtotal from the order; propose a default deposit using the legacy threshold rule (`MIN_CONTRACT_ADVANCE` / `MAX_CONTRACT_ADVANCE` / `TOTAL_CONTRACT_MIN`, §6.4); allow overriding discount, deposit, and extra charge, recalculating total and balance live. Done when overriding any of the three fields updates total/balance immediately without a page reload.
  - `src/lib/deposit.ts` + `src/lib/deposit-config.ts` (reads the three env vars) implement the threshold rule as a pure function, unit-tested in `src/lib/deposit.test.ts` (real assertions, no DB needed — pure calculation). `step-confirm.tsx` recomputes total/balance from live component state on every override, no server round-trip.

- [x] **6. Confirm-and-create endpoint.** A single server action/route handler that receives the full wizard payload, generates `folio` and `viewerToken`, re-validates and recomputes totals server-side (never trusting client-sent totals as final), and writes `contracts`, `contract_packages` (with `nameSnapshot`/`priceSnapshot`), and `contract_service_selections` in one database transaction. Done when a successful call creates all three sets of rows atomically — a failure partway through must roll back everything, not leave a partial contract.
  - `src/app/(app)/contratos/actions.ts`'s `createContract` — real `prisma.$transaction(async (tx) => {...})` wrapping the `contract.create` + `contractPackage.createMany` + `contractServiceSelection.createMany` calls (confirmed by reading the file; all three writes happen against the same `tx`, so a mid-transaction failure rolls back automatically — this is Prisma's interactive-transaction guarantee, not something that needed a separate manual test). Server-side re-validates: package still exists and `active`, quantity within `maxQuantity`, price pulled fresh from `packagePrices` for the selected price list (never trusts a client-sent price), required service selections re-checked against the packages actually in the order. `folio` generated via `src/lib/contracts/folio.ts`'s `nextFolio` (count-based, `CT-####`, per design-system.md §3's format), with retry-on-`P2002`-collision up to 3 attempts if two confirms race — a real edge case handled, not assumed away.
  - **Deliberate, documented deviation from the "use `scopeToOwner`" convention established for this sprint**: this action doesn't use `scopeToOwner` — it only ever creates rows (never reads/updates/deletes an existing contract, and `create`/`createMany` are excluded from `scopeToOwner`'s scoping by design per `src/lib/authorization.ts`), and using it anyway would hit a real TypeScript limitation where `$transaction`'s overloaded signature doesn't resolve cleanly against `scopeToOwner`'s `PrismaClient | ExtendedClient` return type. Explained in a code comment. `scopeToOwner` is used correctly by the list/detail pages (task 8), which do real scoped reads.

- [x] **7. Enforce ownership on creation.** `createdById` is set from the authenticated session server-side, never from client input, per the §5 permission matrix. Done when a request with a spoofed `createdById` in the payload is ignored and the contract is still correctly attributed to the actual logged-in user.
  - Confirmed by reading `actions.ts` line-by-line: `createdById: session.user.id` is hardcoded into the `tx.contract.create` call. The zod schema (`createContractPayloadSchema` in `nuevo/schema.ts`) has no `createdById` field at all, so even if a malicious client sent one in the raw request body, `zod.safeParse` would strip it before it ever reached the create call — there is no code path where client input could reach this field.

- [x] **8. Contract list and detail views (read-only).** A list respecting §5 visibility (only own contracts for `normal`, all for `super`), and a detail page rendering the confirmed contract's data, packages, and service selections. Done when a `normal` user's list never includes another user's contracts, and the detail page displays line items from the `contract_packages` snapshot — not by joining to live `packages` data.
  - `src/app/(app)/contratos/page.tsx` (list) and `src/app/(app)/contratos/[id]/page.tsx` (detail) both call `scopeToOwner(session)` for their Prisma queries — confirmed by reading both files. Both use the new `StatusPill` domain component (`src/components/status-pill.tsx`, built this sprint — the first real consumer of the component design-system.md called for since Sprint 2) for `contractStatus`/`paymentStatus`. Detail page reads `line.nameSnapshot`/`line.priceSnapshot` directly off `contract_packages` rows — confirmed no query anywhere joins back to live `packages`/`packagePrices` for display.
  - **Live-verified against the real dev server and real database** (throwaway fixtures: two `normal` users, one contract each, deleted after use — same pattern as every prior sprint): owner's `GET /contratos` list contained `CT-V001` (own) and did **not** contain `CT-V002` (other user's). Direct-URL access to the other user's contract detail (`GET /contratos/<other-id>`) returned `404` (not `403` — `scopeToOwner`'s `findUnique` correctly returns `null` for a row outside the scope, which the page turns into `notFound()`), while the owner's own contract detail returned `200`.
  - Added `/contratos` to `src/lib/navigation.ts`'s `NAV_ITEMS` (`role: "normal"` — visible to both roles, matching spec §5's "Contracts — list/view: Yes for both, scoped by ownership for normal") so it appears in the sidebar; `src/lib/navigation.test.ts` extended to cover it.
