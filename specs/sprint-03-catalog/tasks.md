- [x] **2. Price lists CRUD.** `super`-only create/edit/delete for `price_lists`, including a "set as default" action. Done when marking one list as default automatically unsets `is_default` on any previously-default list — spec §6.9 requires exactly one default at all times, enforced here at the application layer since the database doesn't guarantee it.
  - `src/app/listas-precios/` — `page.tsx`, `create-price-list-dialog.tsx`, `price-list-row-actions.tsx`, `actions.ts` (`createPriceList`, `updatePriceList`, `setPriceListActive`, `setPriceListDefault`, `deletePriceList`).
  - **Decision (not explicit in spec, resolved here):** the very first price list ever created is made default automatically (`createPriceList` checks `existingCount === 0`), since spec §6.9's "exactly one default at all times" would otherwise be briefly violated (zero defaults) the moment the first list exists with no UI action yet taken to mark it default. `setPriceListDefault` wraps the unset-old/set-new pair in `prisma.$transaction([...])` so a crash mid-way can never leave two defaults or zero.
  - **Decision (extending task 7's guard to price lists, since the "done when" for task 7 only names categories/services but `price_lists` has the exact same FK-restrict shape):** `deletePriceList` refuses to delete the current default list (would break the "exactly one default" invariant with no automatic promotion) and also blocks when `package_prices` or `contracts` still reference it, with a message naming counts of each.
  - Verified live: real DB test (`src/app/catalog.test.ts`) proves `setPriceListDefault` actually unsets the old default and sets the new one against real rows (not asserted from reading the code). Route-level: `super` → `200` on `/listas-precios`, `normal` → `307`. `tsc`/`eslint`/`vitest` clean.

- [x] **3. Packages CRUD.** `super`-only create/edit/delete for `packages`, including `maxQuantity`/`quantityUnit` (for items like LED screens with a bounded quantity) and the `active` toggle. Done when a package can be created with or without a quantity limit, and toggling `active` hides it from the store-mode catalog used in Sprint 4 without deleting it.
  - `src/app/paquetes/page.tsx` (list + create dialog), `create-package-dialog.tsx`, `package-row-actions.tsx` (active toggle + delete-confirm; "Editar" is a `Link` to `/paquetes/[id]`, not a dialog — see tasks 5/6 for why), `actions.ts` (`createPackage`, `updatePackage`, `setPackageActive`, `deletePackage`, plus `setPackageServices`/`savePackagePrice` for tasks 5/6).
  - `maxQuantity`/`quantityUnit` are both optional and independent in the form (empty `maxQuantity` → `null`, meaning "quantity fixed at 1" per spec §6.3) — the spec doesn't require them to be filled in together, so no cross-field validation was added beyond that.
  - `active` toggling (`setPackageActive`) only flips the boolean column — task 3 explicitly requires this not to delete anything, and Sprint 4's store-mode catalog query is expected to filter `WHERE active = true` when it's built (not this sprint's scope). `src/app/catalogo/page.tsx` (task 8) already filters `packages: { where: { active: true } }` as a preview of that same filter, proving the column has a real read-side consumer even before Sprint 4.
  - Verified live: real throwaway package inserted via Prisma (category "Sonido e iluminación (verificación)", `maxQuantity: 2`, `quantityUnit: "pantallas"`) rendered correctly on `/paquetes` ("Hasta 2 pantallas") and on `/catalogo`. Route-level `super`/`normal` split confirmed the same way as task 1. Cleaned up after.

- [x] **4. Services CRUD.** `super`-only create/edit/delete for `services`, including the `options` field (an editable list of strings for "choose 1 of N" services — spec §6.6). Done when a service can be created with zero or more options, and the options list can be reordered/edited after creation.
  - `src/components/options-editor.tsx` — new reusable, fully-controlled (`value`/`onChange`, not `useFieldArray`) editable-list control: add/remove/move-up/move-down per option, wired into both the create and edit forms via react-hook-form's `Controller` (kept controlled rather than generic-`useFieldArray` specifically to avoid the `watch()`-style React Compiler memoization trap already documented in this project's conventions).
  - `src/app/servicios/` — `page.tsx`, `create-service-dialog.tsx`, `service-row-actions.tsx`, `actions.ts` (`createService`, `updateService`, `deleteService`). Empty-string options are filtered out before persisting; an empty resulting array is stored as SQL `NULL` (via `Prisma.JsonNull` on update — a real Prisma gotcha hit and fixed here: assigning plain `null` to a nullable `Json` field in an `update` doesn't mean "set to database NULL" the way it does for other column types, `Prisma.JsonNull` is required), matching spec §6.6's "null/empty for services with no choice."
  - Verified live: real throwaway service with two options ("4 horas"/"6 horas") rendered on `/servicios` (badge "2 opciones") and its options + selection round-tripped correctly into the package edit page's services checklist (task 5) and the RSC payload inspected directly (`selectedServiceIds` matched). Route-level split confirmed. Cleaned up after.

- [x] **5. Package ↔ service association.** Within the package edit page, manage which `services` are included via `package_services` (spec §6.7) — a multi-select or checklist UI. Done when adding/removing a service from a package persists correctly and is reflected immediately when viewing that package.
  - `src/app/paquetes/[id]/page.tsx` is the "package edit page" the task refers to (this is why task 3's row action links here instead of using a dialog — services and prices need real page real-estate, not a small modal). `package-services-editor.tsx`: a checklist grouped by category, backed by local `Set<string>` state seeded from `pkg.packageServices`, with a single "Guardar servicios" button calling `setPackageServices(packageId, serviceIds)`.
  - `setPackageServices` (in `paquetes/actions.ts`) is replace-all, not incremental add/remove: one `$transaction([deleteMany({packageId}), createMany(...)])`. This was a deliberate simplification over diffing added/removed ids — the UI's checklist state is already the full desired set, so replace-all is both simpler and can't drift from an add/remove bug.
  - Verified with a real-DB test (`src/app/catalog.test.ts`): calling `setPackageServices` twice with different id sets proves the second call fully replaces the first (not additive) against real `package_services` rows. Also confirmed live via the RSC payload inspection described in task 4's note (`selectedServiceIds` reflected the real linked row after a direct Prisma insert). Dialog-click interaction itself (checking a box, clicking "Guardar servicios" in a real browser) was **not** verified — no headless browser tool available in this environment, same limitation noted throughout Sprint 2.

- [x] **6. Package prices per price list.** Within the package edit page, set/edit the `package_prices` row (spec §6.10) for each price list. Done when editing the price for one price list does not affect the package's price in any other list, and a newly-created price list starts with no price set for existing packages (must be filled in explicitly, not defaulted or copied).
  - `package-prices-editor.tsx`: one table row per price list, each an independent mini-form (its own `useState`/`useTransition`, own "Guardar" button) rather than one big form for every list — chosen so a mistake on one list's price can't block saving another, and so partial saves are visible per-row. `savePackagePrice(packageId, priceListId, price)` upserts on the `(package_id, price_list_id)` unique constraint when `price` is a number, or **deletes** the row when `price` is `null` — a cleared price becomes "not set" again rather than a stored zero, keeping that a real distinguishable state (used by `/catalogo`'s "Sin precio en esta lista" label).
  - The "new price list starts with no price" half of this task's "done when" isn't code that had to be written — it's the *absence* of any auto-seeding logic in `createPriceList` (task 2). Confirmed explicitly with a real-DB test: a `package_prices` lookup for a package against a just-created price list returns `null` before anything is set.
  - Also added `src/components/money.tsx` — the `Money` domain component required by `docs/design-system.md` §2 ("single source of truth for monetary formatting... do not call `Intl.NumberFormat` ad hoc elsewhere"). This is the first screen in the app that renders a peso amount, so it had to exist before `/catalogo` (task 8) could show a package's price without violating that rule.
  - Verified with a real-DB test: setting a price on list A and confirming list B (for the same package) is unaffected; then clearing list A's price and confirming the row is deleted, not zeroed. Also confirmed live: a real `package_prices` row (12500.00) rendered as "$12,500.00" via `Money` on `/catalogo`.

- [x] **7. Referential-integrity guards on delete.** Deleting a `category` or `service` that is still referenced (by a `package`, or by `package_services`) must be blocked with a clear error rather than silently cascading — packages already snapshot their own data into contracts at selection time (spec §6.5), but the catalog itself should stay consistent. Done when attempting to delete a referenced category or service fails with a message identifying what's still using it.
  - Confirmed first (`prisma/migrations/20260828064535_init/migration.sql`) that every relevant FK is already `ON DELETE RESTRICT ON UPDATE CASCADE` at the database level — so the invariant was never actually at risk of silent cascading; the gap this task closes is a **friendly, specific message** instead of a raw Postgres constraint-violation error bubbling up.
  - `deleteCategory` checks both `packages.category_id` and `services.category_id` (categories are referenced by both, not just packages — read the task text as "referenced by a package" and "referenced by package_services" describing the two *kinds* of reference the sprint anticipated, not an exhaustive list; checking both FKs on each entity is the more correct reading of "the catalog itself should stay consistent"). `deleteService` checks `package_services.service_id` **and** `contract_service_selections.service_id` (a service already chosen on a real contract must never be deletable either). Both return a message naming the referencing counts, e.g. "No se puede eliminar: todavía hay 2 paquetes y 1 servicio que usan esta categoría."
  - **Extended beyond the task's literal scope, deliberately:** the exact same FK-restrict shape exists for `packages` (blocked by `contract_packages`) and `price_lists` (blocked by `package_prices`/`contracts`) — leaving those to throw a raw Prisma/Postgres error on the delete buttons built in tasks 2/3 would have been a real bug, not a scope boundary, so `deletePackage`/`deletePriceList` got the same treatment (see tasks 2/3's notes). `deletePackage` additionally distinguishes "used by a real contract" (hard block) from "has its own `package_services`/`package_prices` rows" (cleaned up automatically in the same transaction as the delete, since those are owned by the package, not independent catalog entities).
  - Verified with real-DB tests (`src/app/catalog.test.ts`): a category referenced by both a package and a service is blocked with both counts named in the message, and still exists afterward; a service referenced by `package_services` is blocked and still exists afterward; a package referenced by a real `contract_packages` row is blocked (message names the contract count) and still exists afterward.

Enforce at the route level — not just by hiding buttons — that `normal` users cannot reach any create/edit/delete action, consistent with the Sprint 2 authorization layer (spec §5). Done when a `normal`-role request to a catalog write endpoint is rejected even if made directly (e.g. via curl), not only blocked in the UI.
  - `src/app/catalogo/page.tsx` + `price-list-switcher.tsx`: read-only, both roles (spec §5's catalog row is read-open, not `super`-only), grouped by category, only `active` packages, price under a `?lista=<id>` query param defaulting to the default price list. No forms, no server actions that mutate anything are reachable from this page at all — there was nothing on it to gate per-button, since it contains zero write affordances by construction.
  - **Spec-ambiguity resolved:** `docs/design-system.md` §4's screen-reference table has no "Catálogo"/browsing screen mapped to Sprint 3 (it jumps from `Configuracion` straight past this) — there was no mockup to build against. Reused the established component vocabulary (`Card`, `Badge`, the new `Money`) rather than inventing new visual conventions, per the design system's own instruction not to improvise ad hoc when unsure; flagging this gap explicitly rather than silently treating an invented layout as "the" design.
  - **Route naming decision:** `/categorias`, `/servicios`, `/listas-precios`, `/paquetes` (+`/paquetes/[id]`) are `super`-only CRUD screens, added to `src/proxy.ts`'s `SUPER_ONLY_PREFIXES`; `/catalogo` is the separate read-only browsing screen for both roles, deliberately **not** added to that list. `normal` users get read access to packages/services/prices through `/catalogo` only — they were not given a raw admin list of categories, since task 8 only asked for "browse packages by category," not full parity with the `super` admin screens.
  - **How "rejected even if made directly" was actually verified — read carefully, this is the one task-level claim in this sprint that needed a different method than curl:** Next.js Server Actions require the framework's own generated action-id header to invoke over HTTP, which isn't practically obtainable without a headless browser (same "no Playwright" limitation as every UI-interaction gap noted throughout Sprint 2 and this sprint). All 34 pass, and since every action calls `requireRole` as its first line before touching Prisma, none of this needed throwaway DB rows.
  - Also verified live against the real dev server with real throwaway sessions (both roles + anonymous): `/categorias`, `/servicios`, `/listas-precios`, `/paquetes` → `super`=`200`, `normal`=`307`, anon=`307`; `/catalogo` → `super`=`200`, `normal`=`200`, anon=`307`. Confirmed `/catalogo` renders real inserted data correctly for a `normal` session (category, package, its service, and its formatted price `$12,500.00` under the default list), then all verification rows and throwaway users were deleted.
